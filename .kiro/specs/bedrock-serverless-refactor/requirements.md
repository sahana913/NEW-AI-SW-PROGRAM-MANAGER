# Requirements Document

## Introduction

This feature refactors the AI-SW-Program-Manager backend from its current state (~20 scattered Lambda functions, broken SageMaker integration, hardcoded ARNs, and pervasive 500 errors) into a clean, fully serverless AWS architecture. The refactored system consolidates all backend logic into four modular Lambda services, replaces SageMaker with Amazon Bedrock (Claude), fixes all internal server errors, and produces a production-ready deployment with proper CORS, structured logging, environment variable validation, and IAM permissions.

## Glossary

- **AuthService**: The Lambda authorizer function that validates Cognito JWTs and injects `tenantId` and `userId` into the Lambda event context.
- **DocumentService**: The consolidated Lambda service responsible for pre-signed URL generation, S3-event-triggered document processing, and Amazon Textract text extraction.
- **PredictionAnalyticsService**: The consolidated Lambda service responsible for project risk analysis, delay prediction, and workload analysis using Amazon Bedrock (Claude).
- **DashboardAPIService**: The consolidated Lambda service responsible for dashboard overview, project summaries, health scores, and report generation using Amazon Bedrock.
- **Bedrock_Client**: The boto3 wrapper that invokes Amazon Bedrock Runtime (`bedrock-runtime`) with model ID `anthropic.claude-3-5-sonnet-20241022-v2:0`.
- **Heuristic_Engine**: The fallback scoring module that computes delay probability and risk level from sprint velocity and milestone data without calling Bedrock.
- **CDK_App**: The AWS CDK application (`infrastructure/app.py`) that synthesizes and deploys all stacks.
- **StorageStack**: The CDK stack that provisions S3 buckets and the pre-signed URL Lambda.
- **DynamoDBStack**: The CDK stack that provisions all DynamoDB tables.
- **APIGatewayStack**: The CDK stack that provisions API Gateway and the four consolidated Lambda functions.
- **AuthStack**: The CDK stack that provisions the Cognito User Pool and the AuthService Lambda authorizer.
- **Pre_Signed_URL**: A time-limited S3 URL generated by DocumentService that allows the frontend to upload a file directly to S3 without routing through API Gateway.
- **Tenant**: An isolated organizational unit identified by `tenantId`, extracted from the Cognito JWT and injected into every Lambda invocation.
- **RAG_Status**: A Red/Amber/Green project health indicator derived from the health score (RED < 60, AMBER 60–79, GREEN ≥ 80).
- **Cold_Start**: The initialization latency incurred when AWS Lambda provisions a new execution environment for a function that has not been recently invoked.

## Requirements

### Requirement 1: Lambda Consolidation

**User Story:** As a platform engineer, I want the backend consolidated from ~20 Lambda functions into 4 modular services, so that the system is easier to deploy, debug, and maintain.

#### Acceptance Criteria

1. THE CDK_App SHALL deploy exactly four application Lambda functions: `AuthService`, `DocumentService`, `PredictionAnalyticsService`, and `DashboardAPIService`.
2. WHEN the CDK_App is synthesized, THE CDK_App SHALL NOT create any Lambda function outside the four consolidated services and the AuthService Lambda authorizer.
3. THE APIGatewayStack SHALL remove all Lambda functions that existed prior to consolidation (analysis_trigger, audit_logging, azure_devops_integration, data_storage, data_validation, database_maintenance, document_intel, document_intelligence, document_upload, email_distribution, health_score, jira_integration, pdf_export, rag_status, report_scheduling, risk_detection, security_monitoring, semantic_search, user_management) and SHALL NOT reference their handler paths.
4. WHEN a request is routed to a consolidated service, THE APIGatewayStack SHALL invoke the correct Lambda function based on the API Gateway resource path.

### Requirement 2: CDK Stack Structure

**User Story:** As a platform engineer, I want the CDK infrastructure reduced to exactly four stacks, so that the deployment is predictable and free of orphaned resources.

#### Acceptance Criteria

1. THE CDK_App SHALL contain exactly four stacks: `StorageStack`, `DynamoDBStack`, `APIGatewayStack`, and `AuthStack`.
2. THE CDK_App SHALL NOT instantiate `AuditLoggingStack`, `SharedStack`, or any other stack beyond the four required stacks.
3. THE StorageStack SHALL provision the documents S3 bucket, the reports S3 bucket, and the pre-signed URL Lambda.
4. THE StorageStack SHALL NOT provision a `ModelArtifactsBucket` or any SageMaker-related resource.
5. THE DynamoDBStack SHALL retain all existing DynamoDB tables (UsersTable, IntegrationsTable, RisksTable, PredictionsTable, ReportsTable, DocumentsTable, ProjectsTable, SprintsTable, BacklogItemsTable, MilestonesTable, ResourcesTable, DependenciesTable, HealthScoresTable, CacheTable).
6. THE AuthStack SHALL provision the Cognito User Pool, the Cognito User Pool Client, and the AuthService Lambda authorizer.
7. THE APIGatewayStack SHALL provision the API Gateway REST API and the four consolidated Lambda functions.

### Requirement 3: SageMaker Removal and Bedrock Integration

**User Story:** As a product owner, I want SageMaker replaced with Amazon Bedrock (Claude), so that AI predictions and report generation work without requiring a separately provisioned ML endpoint.continue working

#### Acceptance Criteria

1. THE CDK_App SHALL NOT create, reference, or pass any SageMaker endpoint ARN or environment variable (`DELAY_CLASSIFIER_ENDPOINT`, `DELAY_REGRESSOR_ENDPOINT`, `WORKLOAD_ENDPOINT`) to any Lambda function.
2. WHEN the PredictionAnalyticsService is invoked, THE Bedrock_Client SHALL call `bedrock-runtime` with model ID `anthropic.claude-3-5-sonnet-20241022-v2:0` to generate delay predictions and risk analysis.
3. WHEN the DashboardAPIService generates a report, THE Bedrock_Client SHALL call `bedrock-runtime` with model ID `anthropic.claude-3-5-sonnet-20241022-v2:0` to produce the report narrative.
4. IF a Bedrock_Client call raises an exception, THEN THE Heuristic_Engine SHALL compute a fallback score and THE PredictionAnalyticsService SHALL return the fallback result with a `fallback: true` flag in the response body.
5. THE APIGatewayStack SHALL grant `bedrock:InvokeModel` on `arn:aws:bedrock:*::foundation-model/anthropic.claude-3-5-sonnet-20241022-v2:0` to both `PredictionAnalyticsService` and `DashboardAPIService`.

### Requirement 4: Document Upload Flow

**User Story:** As a user, I want to upload project documents (PDF, DOCX, TXT) and have them automatically processed, so that the system can extract text and make the content available for analysis.

#### Acceptance Criteria

1. WHEN a POST request is made to `/documents/upload` with a valid `fileName`, `contentType`, `projectId`, and `fileSize` ≤ 52,428,800 bytes (50 MB), THE DocumentService SHALL return HTTP 200 with a `uploadUrl` (pre-signed S3 PUT URL) and a `documentId`.
2. WHEN a file is PUT to the pre-signed URL and the S3 `ObjectCreated` event fires, THE DocumentService SHALL be invoked via the S3 event notification and SHALL update the document status in DynamoDB to `PROCESSING`.
3. WHEN the DocumentService processes an S3 event, THE DocumentService SHALL call Amazon Textract to extract text from the uploaded document and SHALL store the extracted text in DynamoDB with status `PROCESSED`.
4. IF the uploaded file's `contentType` is not `application/pdf`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document`, or `text/plain`, THEN THE DocumentService SHALL return HTTP 400 with error code `UNSUPPORTED_FILE_TYPE`.
5. IF the `fileSize` exceeds 52,428,800 bytes, THEN THE DocumentService SHALL return HTTP 400 with error code `FILE_TOO_LARGE`.
6. THE StorageStack SHALL configure an S3 `ObjectCreated` event notification on the documents bucket that targets the DocumentService Lambda.

### Requirement 5: Prediction and Risk Analysis

**User Story:** As a project manager, I want AI-powered delay predictions and risk analysis for my projects, so that I can take proactive action before issues escalate.

#### Acceptance Criteria

1. WHEN a POST request is made to `/predictions/analyze` with a valid `projectId` and the project has at least one sprint or milestone in DynamoDB, THE PredictionAnalyticsService SHALL return HTTP 200 with a response body containing `delay_probability` (a float in the range [0.0, 1.0]), `risk_level` (one of `LOW`, `MEDIUM`, or `HIGH`), and `reasoning` (a non-empty string).
2. WHEN the PredictionAnalyticsService computes `delay_probability`, THE PredictionAnalyticsService SHALL store the result in the PredictionsTable with a `prediction_id`, `project_id`, `tenant_id`, `created_at`, and `model_version` attribute.
3. IF the project has no sprints and no milestones in DynamoDB, THEN THE PredictionAnalyticsService SHALL return HTTP 422 with error code `INSUFFICIENT_DATA`.
4. IF the Bedrock_Client call fails, THEN THE Heuristic_Engine SHALL compute `delay_probability` from sprint velocity variance and milestone completion percentage, and THE PredictionAnalyticsService SHALL include `"fallback": true` in the response body.
5. WHEN the Heuristic_Engine computes `delay_probability`, THE Heuristic_Engine SHALL assign `risk_level` as `LOW` when `delay_probability` < 0.4, `MEDIUM` when 0.4 ≤ `delay_probability` < 0.7, and `HIGH` when `delay_probability` ≥ 0.7.

### Requirement 6: Dashboard API

**User Story:** As a user, I want the dashboard to display real project data from DynamoDB, so that I can monitor portfolio health without seeing hardcoded demo data.

#### Acceptance Criteria

1. WHEN a GET request is made to `/dashboard/overview` with a valid Cognito JWT, THE DashboardAPIService SHALL return HTTP 200 with a response body containing `projects` (a list of project summaries from DynamoDB), `portfolioHealth`, `recentRisks`, and `upcomingMilestones`.
2. THE DashboardAPIService SHALL NOT return hardcoded or static demo data in any response field.
3. WHEN the DashboardAPIService queries DynamoDB and the tenant has no projects, THE DashboardAPIService SHALL return HTTP 200 with an empty `projects` list and zeroed `portfolioHealth` metrics.
4. IF DynamoDB is unavailable or returns a service error, THEN THE DashboardAPIService SHALL return HTTP 503 with error code `SERVICE_UNAVAILABLE`.
5. WHEN a POST request is made to `/reports/generate` with a valid `reportType` and `projectIds`, THE DashboardAPIService SHALL invoke the Bedrock_Client to generate a report narrative and SHALL return HTTP 200 with the report content.

### Requirement 7: Authentication Preservation

**User Story:** As a security engineer, I want all existing Cognito JWT validation behavior preserved, so that the refactored system maintains the same authentication guarantees.

#### Acceptance Criteria

1. WHEN an API Gateway request is received without an `Authorization` header, THE AuthService SHALL return a 401 Unauthorized policy that denies access to all resources.
2. WHEN an API Gateway request is received with an `Authorization` header containing an invalid or expired Cognito JWT, THE AuthService SHALL return a 401 Unauthorized policy.
3. WHEN an API Gateway request is received with a valid Cognito JWT, THE AuthService SHALL return an Allow policy and SHALL inject `tenantId` and `userId` into the Lambda event context under `requestContext.authorizer`.
4. THE AuthStack SHALL configure the API Gateway `RequestAuthorizer` with `Authorization` as the sole identity source and a results cache TTL of 5 minutes.
5. THE AuthService SHALL NOT depend on any middleware package that is not bundled in the Lambda deployment package.

---

### Requirement 8: API Gateway Routes

**User Story:** As a frontend developer, I want all required API routes defined and reachable, so that the frontend can communicate with the backend without 404 or 403 errors.

#### Acceptance Criteria

1. THE APIGatewayStack SHALL define the following routes: `POST /documents/upload`, `POST /documents/process`, `POST /predictions/analyze`, `GET /dashboard/overview`, and `POST /reports/generate`.
2. WHEN a preflight `OPTIONS` request is made to any of the five routes, THE APIGatewayStack SHALL return HTTP 200 with `Access-Control-Allow-Origin: *`, `Access-Control-Allow-Methods: OPTIONS,GET,POST`, and `Access-Control-Allow-Headers: Content-Type,Authorization`.
3. THE APIGatewayStack SHALL attach the AuthService Lambda authorizer to all routes except `OPTIONS` preflight requests.
4. WHEN a request is made to a route that does not exist, THE APIGatewayStack SHALL return HTTP 404 with `Access-Control-Allow-Origin: *` in the response headers.

### Requirement 9: Environment Variable Validation

**User Story:** As a platform engineer, I want all Lambda functions to validate required environment variables at startup, so that misconfigured deployments fail fast with a clear error rather than returning 500 at runtime.

#### Acceptance Criteria

1. WHEN a Lambda function initializes its module-level code, THE Lambda function SHALL read all required environment variables and SHALL raise a `EnvironmentError` with a descriptive message listing the missing variable names if any required variable is absent or empty.
2. THE DocumentService SHALL require the following environment variables: `DOCUMENTS_BUCKET`, `DOCUMENTS_TABLE_NAME`, `AWS_REGION`.
3. THE PredictionAnalyticsService SHALL require the following environment variables: `PREDICTIONS_TABLE_NAME`, `PROJECTS_TABLE_NAME`, `SPRINTS_TABLE_NAME`, `MILESTONES_TABLE_NAME`, `AWS_REGION`.
4. THE DashboardAPIService SHALL require the following environment variables: `PROJECTS_TABLE_NAME`, `HEALTH_SCORES_TABLE_NAME`, `RISKS_TABLE_NAME`, `PREDICTIONS_TABLE_NAME`, `REPORTS_TABLE_NAME`, `AWS_REGION`.
5. THE AuthService SHALL require the following environment variables: `USER_POOL_ID`, `AWS_REGION`.
6. IF a required environment variable is missing, THEN THE Lambda function SHALL log the error to CloudWatch with level `ERROR` before raising the exception.

### Requirement 10: IAM Permissions

**User Story:** As a platform engineer, I want all Lambda functions to have exactly the IAM permissions they need, so that the principle of least privilege is enforced and no function fails due to missing permissions.

#### Acceptance Criteria

1. THE APIGatewayStack SHALL grant `DocumentService` the following permissions: `s3:PutObject` and `s3:GetObject` on the documents bucket, `dynamodb:PutItem`, `dynamodb:GetItem`, `dynamodb:UpdateItem`, and `dynamodb:Query` on DocumentsTable, and `textract:AnalyzeDocument`, `textract:DetectDocumentText`, `textract:StartDocumentTextDetection`, `textract:GetDocumentTextDetection` on `*`.
2. THE APIGatewayStack SHALL grant `PredictionAnalyticsService` the following permissions: `dynamodb:PutItem`, `dynamodb:GetItem`, `dynamodb:Query` on PredictionsTable, `dynamodb:Query` on ProjectsTable, SprintsTable, and MilestonesTable, and `bedrock:InvokeModel` on the Claude model ARN.
3. THE APIGatewayStack SHALL grant `DashboardAPIService` the following permissions: `dynamodb:GetItem`, `dynamodb:Query`, `dynamodb:Scan` on ProjectsTable, HealthScoresTable, RisksTable, PredictionsTable, and ReportsTable, `dynamodb:PutItem` on ReportsTable, and `bedrock:InvokeModel` on the Claude model ARN.
4. THE APIGatewayStack SHALL grant `AuthService` the following permissions: `cognito-idp:GetUser` on the Cognito User Pool ARN.
5. THE APIGatewayStack SHALL NOT grant any Lambda function `sagemaker:InvokeEndpoint` permission.

### Requirement 11: Structured Logging and Error Handling

**User Story:** As an operations engineer, I want centralized structured logging and consistent error handling across all Lambda functions, so that I can diagnose issues quickly in CloudWatch.

#### Acceptance Criteria

1. THE DocumentService, PredictionAnalyticsService, DashboardAPIService, and AuthService SHALL emit all log entries as JSON objects to CloudWatch Logs with at minimum the fields `level`, `message`, `service`, `tenant_id`, and `timestamp`.
2. WHEN an unhandled exception occurs in any Lambda handler, THE Lambda function SHALL catch the exception, log it at level `ERROR` with the full stack trace, and return HTTP 500 with body `{"error": {"code": "INTERNAL_ERROR", "message": "An unexpected error occurred"}}`.
3. WHEN a validation error occurs (missing required field, invalid value), THE Lambda function SHALL return HTTP 400 with body `{"error": {"code": "VALIDATION_ERROR", "message": "<description>"}}`.
4. WHEN an authorization error occurs, THE Lambda function SHALL return HTTP 403 with body `{"error": {"code": "FORBIDDEN", "message": "Access denied"}}`.
5. THE APIGatewayStack SHALL configure gateway responses for `DEFAULT_4XX` and `DEFAULT_5XX` to include `Access-Control-Allow-Origin: *` in the response headers.

### Requirement 12: CORS Configuration

**User Story:** As a frontend developer, I want CORS correctly configured on all API routes and error responses, so that the React frontend can call the API from any origin without browser-level CORS errors.

#### Acceptance Criteria

1. THE APIGatewayStack SHALL configure `default_cors_preflight_options` with `allow_origins=["*"]`, `allow_methods=["OPTIONS","GET","POST","PUT","DELETE"]`, and `allow_headers=["Content-Type","Authorization","X-Amz-Date","X-Api-Key","X-Amz-Security-Token"]`.
2. WHEN any Lambda function returns an HTTP response, THE Lambda function SHALL include `Access-Control-Allow-Origin: *` in the response headers.
3. THE APIGatewayStack SHALL add gateway responses for `DEFAULT_4XX`, `DEFAULT_5XX`, `UNAUTHORIZED`, and `ACCESS_DENIED` that include `Access-Control-Allow-Origin: '*'` in the response headers.
4. WHEN an `OPTIONS` request is received by any Lambda handler, THE Lambda function SHALL return HTTP 200 with the CORS headers and an empty body without invoking the authorizer.

### Requirement 13: Cold Start Optimization

**User Story:** As a user, I want Lambda cold starts minimized, so that the first request after a period of inactivity does not time out or feel unacceptably slow.

#### Acceptance Criteria

1. THE APIGatewayStack SHALL package each of the four consolidated Lambda functions from its own source directory, excluding test files, `__pycache__`, and development-only dependencies.
2. THE APIGatewayStack SHALL configure a Lambda Layer containing shared dependencies (`boto3`, `aws-lambda-powertools`) and SHALL attach it to all four consolidated Lambda functions.
3. THE DocumentService, PredictionAnalyticsService, and DashboardAPIService SHALL be configured with a memory size of at least 512 MB to reduce initialization time.
4. THE AuthService SHALL be configured with a memory size of at least 256 MB.
5. THE APIGatewayStack SHALL NOT configure any Lambda function with a VPC, as VPC attachment significantly increases cold start latency.

### Requirement 14: No Prohibited Infrastructure

**User Story:** As a platform engineer, I want the deployment to contain no VPC, OpenSearch, ElastiCache, EC2, or SageMaker resources, so that the architecture is purely serverless and avoids unnecessary cost and complexity.

#### Acceptance Criteria

1. THE CDK_App SHALL NOT create any `ec2.Vpc`, `ec2.Subnet`, or `ec2.SecurityGroup` construct.
2. THE CDK_App SHALL NOT create any `opensearch.Domain` or `elasticsearch.Domain` construct.
3. THE CDK_App SHALL NOT create any `elasticache.CfnReplicationGroup` or `elasticache.CfnCacheCluster` construct.
4. THE CDK_App SHALL NOT create any `ec2.Instance` or `autoscaling.AutoScalingGroup` construct.
5. THE CDK_App SHALL NOT create any `sagemaker.CfnEndpoint`, `sagemaker.CfnEndpointConfig`, or `sagemaker.CfnModel` construct.

### Requirement 15: Upload API 500 Fix

**User Story:** As a user, I want the document upload API to return a pre-signed URL without errors, so that I can successfully upload documents from the frontend.

#### Acceptance Criteria

1. WHEN a POST request is made to `/documents/upload` with a valid body, THE DocumentService SHALL return HTTP 200 with a `uploadUrl` field and SHALL NOT return HTTP 500.
2. THE DocumentService handler SHALL be located at the module path `document_service.handler.lambda_handler` and THE APIGatewayStack SHALL configure the Lambda `handler` property to this exact path.
3. THE APIGatewayStack SHALL set the `DOCUMENTS_BUCKET` environment variable on the DocumentService Lambda to the `bucket_name` of the documents S3 bucket created in StorageStack.
4. THE APIGatewayStack SHALL set the `DOCUMENTS_TABLE_NAME` environment variable on the DocumentService Lambda to the `table_name` of the DocumentsTable created in DynamoDBStack.
5. IF the DynamoDB `PutItem` call fails when storing document metadata, THEN THE DocumentService SHALL return HTTP 503 with error code `DATABASE_UNAVAILABLE` and SHALL NOT return HTTP 500.

### Requirement 16: Frontend-Backend Connectivity

**User Story:** As a frontend developer, I want the frontend's API service to connect to the correct backend endpoints, so that all dashboard, upload, prediction, and report features work end-to-end.

#### Acceptance Criteria

1. THE APIGatewayStack SHALL export the API Gateway URL as a CloudFormation output named `ApiEndpoint`.

4. WHEN the frontend's `api.ts` calls `POST /predictions/analyze`, THE PredictionAnalyticsService SHALL respond with a structured prediction result.
5. WHEN the frontend's `api.ts` calls `POST /reports/generate`, THE DashboardAPIService SHALL respond with a generated report.

### Requirement 17: Prediction Response Schema

**User Story:** As a frontend developer, I want the prediction API to return a consistent, well-defined response schema, so that the frontend can reliably render prediction charts and risk indicators.

#### Acceptance Criteria

1. THE PredictionAnalyticsService SHALL return a response body that conforms to the following schema: `{ "prediction_id": string, "project_id": string, "delay_probability": float, "risk_level": "LOW"|"MEDIUM"|"HIGH", "reasoning": string, "fallback": boolean, "created_at": ISO-8601 string }`.
2. WHEN `delay_probability` is returned, THE PredictionAnalyticsService SHALL ensure the value is a float in the closed interval [0.0, 1.0].
3. WHEN `risk_level` is returned, THE PredictionAnalyticsService SHALL ensure the value is exactly one of the strings `LOW`, `MEDIUM`, or `HIGH`.
4. WHEN `reasoning` is returned, THE PredictionAnalyticsService SHALL ensure the value is a non-empty string of at least 10 characters.
5. FOR ALL valid project inputs, parsing the response body as JSON and re-serializing it SHALL produce an equivalent JSON string (round-trip property).

### Requirement 18: Heuristic Fallback Correctness

**User Story:** As a product owner, I want the heuristic fallback to produce sensible predictions even when Bedrock is unavailable, so that the system remains useful during AI service outages.

#### Acceptance Criteria

1. WHEN the Heuristic_Engine computes `delay_probability` from sprint data, THE Heuristic_Engine SHALL use the coefficient of variation of sprint velocities as the primary signal, normalized to the range [0.0, 1.0].
2. WHEN the Heuristic_Engine computes `delay_probability` from milestone data, THE Heuristic_Engine SHALL factor in the ratio of overdue milestones to total milestones.
3. WHEN both sprint and milestone data are available, THE Heuristic_Engine SHALL compute `delay_probability` as a weighted average with sprint velocity contributing 60% and milestone overdue ratio contributing 40%.
4. FOR ALL inputs where all sprints have identical velocity and no milestones are overdue, THE Heuristic_Engine SHALL return `delay_probability` = 0.0 and `risk_level` = `LOW`.
5. FOR ALL inputs where velocity coefficient of variation > 0.5 and all milestones are overdue, THE Heuristic_Engine SHALL return `delay_probability` ≥ 0.7 and `risk_level` = `HIGH`.

---

### Requirement 19: DynamoDB Write Reliability

**User Story:** As a platform engineer, I want all DynamoDB writes to be reliable and observable, so that data is never silently lost and failures are surfaced immediately.

#### Acceptance Criteria

1. WHEN the DocumentService writes document metadata to DynamoDB, THE DocumentService SHALL use a conditional expression to prevent overwriting an existing item with the same `document_id`.
2. WHEN the PredictionAnalyticsService writes a prediction result to DynamoDB, THE PredictionAnalyticsService SHALL include a `created_at` ISO-8601 timestamp and a `ttl` attribute set to 90 days from creation.
3. IF a DynamoDB `PutItem` or `UpdateItem` call raises a `ProvisionedThroughputExceededException` or `RequestLimitExceeded` exception, THEN THE Lambda function SHALL retry the operation up to 3 times with exponential backoff before returning an error response.
4. THE DynamoDBStack SHALL configure `point_in_time_recovery=True` on all tables except CacheTable.
5. THE DynamoDBStack SHALL configure `time_to_live_attribute="ttl"` on the CacheTable to enable automatic item expiry.

---

### Requirement 20: Deployment Validation

**User Story:** As a platform engineer, I want the CDK deployment to be validated before and after synthesis, so that configuration errors are caught before they reach AWS.

#### Acceptance Criteria

1. WHEN `cdk synth` is run, THE CDK_App SHALL complete without errors and SHALL produce a CloudFormation template for each of the four stacks.
2. WHEN `cdk deploy` is run, THE CDK_App SHALL deploy all four stacks in dependency order: AuthStack first, then DynamoDBStack and StorageStack in parallel, then APIGatewayStack last.
3. THE APIGatewayStack SHALL declare explicit `add_dependency` calls on AuthStack, DynamoDBStack, and StorageStack to enforce deployment order.
4. WHEN the deployment completes, THE CDK_App SHALL output the API Gateway URL, the Cognito User Pool ID, and the Cognito User Pool Client ID as CloudFormation stack outputs.
5. THE CDK_App SHALL NOT contain any hardcoded AWS account IDs, region strings, or resource ARNs; all such values SHALL be derived from CDK tokens or environment variables.
